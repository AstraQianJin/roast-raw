## 0. 最终裁决（2026-11-13，优先级最高；与下文任何旧描述冲突时以本节为准）

1. **产品与平台**：只做 Web，不做 APP/WebView/APK/iOS；数据存服务器，网页直接读写；不做离线同步、不做本地优先。项目名与界面品牌统一 `Roast Raw`。
2. **仓库与目录**：单仓 `C:\Users\Astra\Desktop\Roast Raw`；每 0.01 本地提交并更新根 `TODO.md`，每 0.10 整倍数验证后推已授权远程。首次仓库归属/名称/可见性先问用户。分层：`web/`（Vue）、`server/`（FastAPI）、`data/`、`tests/`、`docs/`、`Ref/`（只读）；协作入口为根 `AGENTS.md`。
3. **前端**：Vue 3 + Vite + Motion One（~3 KB，MIT），**不引任何 UI 组件库**，样式全手写。纯英文界面，术语写全、该大写的全大写。
4. **后端**：FastAPI + SQLite 单进程，systemd 托管；统计、导入导出、DeepSeek 调用同为 Python，复用既有数据链。
5. **图表**：全部自绘——容量柱用 CSS Grid，趋势线用 SVG polyline，人体热图复用 `body-muscles@1.0.0`（Apache-2.0）路径数据。不引 ECharts / Chart.js / uPlot。
6. **视觉**：编辑部式报表；**浅色默认、深色可切**；高密度信息板；衬线大标题 + 无衬线正文 + 等宽数字；0–4px 圆角、hairline 分隔、无阴影。首页默认落在 **Today**。
7. **角色色**：主项红 / 变式蓝 / 辅项绿，**只用动作名前的小色块 + 行左 2px 边框**，正文与数字保持黑白。强度节点 75 / 85 / 95。
8. **今日页主视觉**：巨型主项重量开场，当日容量条在其下；GEAR 默认折叠，折叠前后都不突兀。
9. **周数不写死**：当前样本 13 周，产品支持任意周数；所有循环、图表、导出、Test Week 均由数据决定，必须用 8 / 17 周合成数据回归。
10. **计划推进**：固定日历、不滑期；没练成就标未完成。所有“今天”与周次边界按 **Asia/Shanghai（北京时间）** 判定。
11. **计划 schema**：新 schema `RPL-Raw-v1`（带 `schemaVersion` 与迁移链），另写 `RPL-Plan-v4 → RPL-Raw-v1` 适配器导入老计划。review JSON 与 plan JSON 是两份独立 schema。
12. **达成率**：先归一化；综合 = 目标 40% + 体重 40% + 完成 20%；完成率 = 主项 60% + 变式 25% + 辅项 15%；可超过 100%，默认不封顶。目标达成率只算 S/B/D 等权，变式与 5 km 只作 PR / 下周期参考。
13. **训练结构**：主项 = Top set + Back-off；热身组自动生成但**只作建议**；Deload 减量不减动作；辅项不写重量，只给组数、次数、目标 RPE。
14. **准备度**：3 主观（肌肉疲劳 / 神经兴奋度 / 饮食热量）+ 3 客观（HRV / 睡眠评分 / 静息心率）+ 训练时段修正（先经验系数，后个人曲线）。**只给建议、永不自动改重量**；插入不低于 70%、调整不超过 -20%。
15. **人体肌群图**：单色相 5 档感知均匀色阶（OKLCH 插值，不用 opacity 叠层、不加模糊）；细线解剖（0.5–0.75px、肌肉间 0.6px 主题分隔线，浅色白缝、深色低亮分隔）；Today/Plan 默认显示精简解剖图与周容量，完整 16 叶列表/参考说明/周期容量板归 Analysis；数值仅在点击/悬停/选择时显示。
16. **动效**：只做点睛——主项重量数字滚动（首次进入一次）、容量柱生长、折叠与切周过渡、趋势线绘制、RPE 胶囊微脉冲、保存对勾描边、人体分区依次淡入、主项重量“盖章”。尊重 `prefers-reduced-motion`。
17. **AI**：服务端调 DeepSeek（`deepseek-chat`，flash 低思考），返回激进/稳定/保守三档；自建最小聊天抽屉做微调；最终 plan JSON 由外部 AI 生成后导入。DeepSeek 失败/无额度：明确报错，并一键导出复盘 JSON + 问卷 JSON + 提示词交给外部 AI，不静默失败。
18. **数据与运维**：免登录、全站单份数据；多设备写入冲突采用**后写覆盖**。备份两层：写入时追加日志流水（重量 × 次数 × RPE），每日整库 SQLite 快照保留 30 份。
19. **里程碑**：0.01 只做地基，按层推进到 0.10 完整闭环；只在 **本地 0.10 完成后的已授权窗口** 部署上线。自动化回归每版全跑，人工验收在 0.10 / 0.20 / 1.10 / 1.20 / 1.30，且新功能必测，另每版随机抽检 20% 旧页面。
20. **命名与红线**：老项目 `C:\Users\Astra\Desktop\RR\ref-projects\roast-powerlifting` 只读；不改、不 git、不部署；老服务器 `49.233.196.202` 不动。新服务器 `82.157.146.30`，ubuntu + `Ref/07_Permissions/RR.pem`，先用 HTTP。

## 4. 数据与统计规则（P0，逐字实现）

### 4.1 动作分类（来自 `day_model.py`）

```
MAIN_MOVES        = {High-bar Squat, Mid-grip Bench, Conventional Deadlift}
SBD_VARIATION     = {Low-bar Squat, Wide-grip Bench, Sumo Deadlift}
POWER_CLEAN_NAMES = {Power Clean, Hang Power Clean, Clean Pull, Clean High Pull}
SNATCH_NAMES      = {Snatch, Power Snatch, Hang Snatch, Snatch Pull, Snatch High Pull, Muscle Snatch}
NON_SBD_VARIATION = {Romanian Deadlift}
```

Bucket 顺序（必须按这个顺序）：

1. name 在 `MAIN_MOVES` → `main`
2. name 在 `SBD_VARIATION` → `sbdVar`
3. `(name 在 POWER_CLEAN_NAMES 或 cat == "D.Vari.Power")` 且 name 不在 `SNATCH_NAMES` → `sbdVar`
4. name 在 `NON_SBD_VARIATION` → `nonSbdVar`
5. 其他 → `accessory`

Lift code：

- High-bar / Low-bar Squat → `S`
- Mid-grip / Wide-grip Bench → `B`
- Conventional / Sumo Deadlift → `D`
- power clean 家族 → `D`
- 其他 → 无

W1 参考：total 71；S main/var 10/3；B 9/4；D 8/6；roles main/sbdVar/accessory = 27/13/31。

### 4.2 16 叶

```
chest, delts_ant, delts_lat, delts_post, triceps, upper_back, lats, erectors,
quads, hamstrings, glutes, adductors, biceps, forearms, core, calves
```

每个动作、每周：

- `weighted[k] += sets × coef[k]`
- `direct[k] += sets`，仅当该叶是 primary。

Primary 规则：

```
mx = max(coef over 16 leaves)
primary   if coef[k] >= mx * 0.8
secondary if coef[k] >= mx * 0.3
direct 只计 primary（tier 1）；secondary 点亮但不计 direct
```

### 4.3 六组

组：`chest, shoulders, back, legs, arms, abs`。

- 每个动作先按行字段 `muscle_group` 折到一组；注意 `lats/upper_back/erectors → back`、`core → abs`、`biceps/triceps/forearms → arms`、`quads/hamstrings/glutes/adductors/calves → legs`、`delts_* → shoulders`。
- `group direct += sets`（每组只计一次）。
- `group weighted += sets × groupCoef`。
- `groupCoef` 是 `muscle_map.json` 的六组 `coef`，也就是 `max(leaf[m]) over group_leaves[g]`，**不是求和**。
- `group_leaves`：`chest=[chest]`、`shoulders=[delts_ant,delts_lat,delts_post]`、`back=[upper_back,erectors,lats]`、`legs=[quads,hamstrings,glutes,adductors]`、`arms=[triceps,biceps]`、`abs=[core]`。`forearms`、`calves` 是 extra leaves，不在六组里。
- 这就是为什么 arms 的 direct 是 0、weighted 是 144.8；不要用 16 叶 max 自己推六组，必须读 `muscle_map`。

### 4.7 Readiness（3 主观 + 3 客观 + 时段，只建议）

- 主观 3 项（1–7）：`muscle_fatigue`（正向）、`neural_arousal`（正向）、`nutrition`（正向）。关节疼痛是独立 flag，触发动作限制，不进均分。
- 客观 3 项：`hrv`（ms）、`sleep_score`（0–100）、`rhr`（bpm）。按个人 28 天均值 ±2σ 截断归一；缺失项跳过，不按 0 计。
- 主观归一：`(v-1)/6*100`；六项等权平均得 `R`；有效项 < 3 不出分。
- `REC = clamp(0.75 + 0.5*(R/100), 0.55, 1.25)`。
- 时段修正（先经验）：14:00–17:00 为基准；早晨 -3%、上午 -1.5%、傍晚 -1%；满 8 周训练时间数据后改个人曲线。
- **只输出建议（如 -5%）与可撤销提示，任何情况下不自动改计划重量**；单次调整上限 -20%，结果不低于 70%。
- 存储键：`<week>|<day>`。

### 4.8 计划 vs 记录

- 统计默认用**计划 sets**。
- 每个动作只记录最后一组：`load × reps @ RPE` + 实际 `sets`。
- 有记录时，该动作的 sets 用记录值；没记录的动作仍用计划值（「未完成的以计划分析」）。
- 记录不是完成度勾选；不要用 0 覆盖未记录。
- 导出 `RPL-Raw-v1`：full + week slice；`logs` 键 `<w>|<day>|<seq>`；`readiness` 键 `<w>|<day>`；派生统计只读。

## 13. 周期归档与 AI 往返（2026-11-13 新需求，P0 数据模型 / P1 UI）

这是用户在这一轮补充的核心工作流，0.01 的数据模型必须为它留好位置，不能假设「永远只有一个计划」。

### 13.1 流程

1. 走完一个计划（当前 13 周，未来任意周数）。
2. 从软件导出 **review JSON**：计划执行的完整记录 + 周期结束状态 + 下个周期展望。
3. 用户把 review JSON 给外部 AI；AI 分析：
   - 上个计划执行得如何；
   - 目标达成率如何；
   - 周期结束水平；
   - 根据这些 + 下个周期的周数/目标，生成新的 **plan JSON**。
4. 用户把新 plan JSON 导入 Web；Web 看到新计划（含新的个人信息）。
5. 旧计划自动归档；归档页可查看旧计划的完成情况/达成率；可打开、可删除；归档 UI 与主界面审美一致。

**注意**：AI 是外部工具，不在 Web 内调用；Web 只负责导出 review、导入 plan、归档和展示。

### 13.2 review JSON 必须包含

- `schema` / `exported_at` / `plan_id` / `app_version`
- `profile_start` / `profile_end`：年龄、身高、体重、目标体重、装备级别等
- `plan`：start、weeks、deload、test、blocks、goals
- `logs`：每个动作最后一组 + 实际组数；完整可追溯
- `readiness`：3 主观 + 3 客观 + 时段修正 + REC（建议层）
- `planned_vs_actual`：每周/每动作计划 vs 实际
- `completion`：sets/reps/load 完成率；deload/test 单独标记
- `attainment`：`composite = 0.40*goal + 0.40*bodyweight + 0.20*completion`；`completion = 0.60*main + 0.25*var + 0.15*acc`；goal 只算 S/B/D 等权
- `e1rm`：主项 e1RM 起点/终点/变化
- `end_state`：测试日 S/B/D max、e1RM、体重、readiness、备注
- `next_outlook`：下个周期周数、目标、体重目标、限制条件、用户展望（用户填写或 AI 生成）
- 版本/完整性字段，便于 AI 和导入校验

### 13.3 plan JSON

- 以**升级后的老 RPL-Plan JSON** 为基础；用户明确要求「JSON 尽可能全」。
- 任意周数；`plan_weeks`、Blocks、Days、Workouts、Anchors、GPP、Goals、deload/test 都由数据决定。
- 导入时校验 schema/版本/字段；新计划导入 = 新周期；旧计划归档，不覆盖日志。
- plan JSON 可包含新的 profile / 目标 / 周数 / 起始日期。

### 13.4 归档

- 多周期：`active` / `completed` / `archived`。

### 13.5 达成率口径（用户 2026-11-13 确认方向）

用户原话要点：

- **计划完成率**：可以超过 100%；主项、变式、辅项**分别追踪**；主项最重要。
- **目标达成率**：最后 test day；可以超过 100%；**权重第一高**。
- **体重**：**权重第二高**。
- 最后给一个**综合分**。

已确认权重（先归一化）：

```
completion_main   = actual_main_sets / planned_main_sets * 100
completion_var    = actual_var_sets / planned_var_sets * 100
completion_acc    = actual_acc_sets / planned_acc_sets * 100
completion        = 0.60*main + 0.25*var + 0.15*acc      // 主项最重要
goal              = test_day_attainment (S/B/D)           // 可 >100
bodyweight        = 目标方向上的接近度                    // 可 >100
composite         = 0.40*goal + 0.40*bodyweight + 0.20*completion
```

- 三项都要独立显示，不只给综合分；综合分要能解释权重。
- >100% 允许显示；综合分是否封顶（100/120/150）待确认。
- test day 的 S/B/D 目标达成：每项 `actual_1rm / target_1rm * 100`；S/B/D 是等权还是主项加权待确认。
- 体重：按目标方向计算；cut 时 actual ≤ target 为达成，bulk 时 actual ≥ target 为达成；具体公式待确认。
- 计划完成率需要区分 deload/test；deload 不拉低完成率，test 单独计。
- review JSON 里要同时存原始数、分项、综合分、权重版本。

| 10 年数据量 | 20 周期 × 13 周 × 4 天 × 6 动作 ≈ 6 万条日志，SQLite 很小（几十 MB 内） | 同样很小，但每年一个目录/文件，文件数会多 |
| 查询/统计 | SQL 直接查、索引、聚合；分析页快 | 每次全量读入内存再算；10 年全量会慢 |
| 一致性 | 事务、外键、崩溃恢复 | 全文件重写，写一半可能坏；要自己写原子替换 |
| 迁移 | schema migration 可控 | 字段变更要批量改文件 |
| 人工查看 | 需要 sqlite 工具 | 直接打开看 |
| 备份 | 单文件拷贝/定时备份 | 目录拷贝，简单 |
| 并发 | 单人足够 | 单人足够，但写入要锁 |
| 依赖 | Python 标准库 `sqlite3`，无额外服务 | 无依赖 |
| 推荐 | **主存储** | **导出/归档/备份格式** |

建议：**SQLite 做服务器主存储 + JSON 导入/导出做备份/迁移**。10 年记录、分析查询、归档删除都更稳；JSON 保留人类可读的导出。
0.01 可先用 SQLite 建 `cycles / plans / logs / readiness / archives` 五张表；导出仍是 `roast-raw/v1` JSON。

## 17. 小型 AI 接口（多轮 + 模型选择）

用户问：**能不能做一个小型 AI 接口，多轮对话 + 选择模型？有没有小型开源项目？实现和维护难吗？**

### 17.1 结论（已确认）

- **已确认：DeepSeek 直连（`deepseek-chat`）+ 自建最小聊天抽屉，只做展望/微调，不做通用聊天**；不引入 Open WebUI/LibreChat。
- 0.01 先做：模型下拉（DeepSeek 两个模型）、消息列表、系统提示词、发送/重试、SQLite 会话历史。
- P1 再加：流式输出、OpenRouter/LiteLLM 多 provider、成本/token 统计、JSON 结构化输出校验。

### 17.2 架构

```
Web 聊天抽屉
  → POST /api/ai/chat   { model, messages, system, json_mode }
  → 服务端读取 DeepSeek.key（或环境变量）
  → 转发到 OpenAI-compatible /v1/chat/completions
  → 返回文本/JSON；会话存 SQLite
```

- 模型列表：`GET /api/ai/models`，静态配置或 provider `/v1/models`。
- 多轮：`messages[]` 存 SQLite；只发最近 N 轮 + 系统提示，避免上下文爆炸。
- 结构化：展望/计划用 `response_format: json_object` 或 JSON schema；服务端校验后再给前端。
- 安全：key 只在服务端；前端不拿 key；请求限流/超时/重试。
- 失败：DeepSeek 没钱/429/超时 → 提示用户切外部 AI；不阻塞主流程。

### 17.3 现成项目对比（不建议直接用）

| 项目 | 形态 | 适不适合 |
|---|---|---|
| Open WebUI | Python/Docker，多用户/RAG/管理台 | 功能全但太重；单人项目不划算 |
| LibreChat | Node/Mongo，多 provider | 重，运维成本高 |
| LobeChat | Next.js，UI 好 | 中等；可作为参考，嵌入仍要改 |
| Chatbot UI | Next.js，轻 | 中等；可以参考布局 |
| Chatbox | 桌面客户端 | 不能嵌进 Web |
| Big-AGI | Next.js | 中等；偏通用 |

**建议**：看 LobeChat/Chatbot UI 的交互，不直接部署；自写 1 个抽屉 + 1 个后端路由，维护最低。

### 17.4 难度

- 最小版（1 provider、非流式、模型下拉、SQLite 历史）：**低**；半天到一天量级。
- 流式 + 多 provider + JSON 校验 + 重试/成本统计：**中**。
- 维护：只要代理保持薄、key 在服务端、不自己造模型协议，维护很低。
- 不建议在 0.01 做 RAG/知识库/多用户/管理台；那是另一个项目。

### 17.5 和本项目的结合

- “AI 展望”不是通用聊天：预置系统提示词 + review JSON + 问卷，输出三档展望。
- 聊天抽屉用于用户追问/微调（“为什么保守档是这个”“把深蹲目标降 2.5kg”），保留多轮上下文。
- 最终 plan JSON 仍由外部 AI 生成；DeepSeek 只负责展望/解释/微调。
- 模型选择默认 `deepseek-chat`；可加 `deepseek-reasoner` 或其他 OpenAI-compatible 模型。

### 17.6 多模型方案对比（下一轮定）

| 方案 | 成本 | 维护难度 | 扩展性 | 说明 |
|---|---|---|---|---|
| DeepSeek 直连 | 最低 | 低 | 单家 | 0.01 默认；`deepseek-chat`/`deepseek-reasoner` |
| OpenRouter | 按量 + 少量加价 | 低 | 高 | 一个 key 接多家模型；模型列表现成；适合“多一点” |
| LiteLLM 自建代理 | 模型费 + 服务器 | 中 | 高 | OpenAI-compatible 网关，多 provider/fallback/预算/日志 |
| OneAPI / NewAPI | 模型费 + 服务器 | 中 | 高 | 自建网关，多 provider、配额/渠道管理；中文生态 |
| 直连多 provider | 各家 key | 中高 | 最高 | 自己写 provider 适配、成本统计、重试 |
| Ollama/vLLM 本地 | 电费/服务器 | 中 | 中 | 4C4G 跑不动好模型；不建议 |

建议：0.01 先 DeepSeek 直连；需要多模型时接 **OpenRouter**（最省事）或 **LiteLLM**（最可控），不要自己写 provider 抽象。

### 17.7 AI 面板方案对比（下一轮定）

| 方案 | 实现成本 | 维护 | 扩展性 | 说明 |
|---|---|---|---|---|
| 自建最小抽屉 | 低 | 低 | 中 | 模型下拉、消息、重试、SQLite；最贴合本项目 |
| LobeChat | 中 | 中 | 高 | UI 成熟，但独立 Next.js 服务，嵌入选型要改 |
| Chatbot UI | 中 | 中 | 中 | 轻量 Next.js；仍需独立部署/改造 |
| 0.01 不做 UI | 最低 | 低 | 低 | 只留 `/api/ai/chat` + 提示词；聊天后置 |

建议：0.01 自建最小抽屉；除非以后要通用聊天/多用户，再考虑 LobeChat。

## 18. 动作库结构（全 261，但重构）

用户 2026-11-13：**「全动作库，但是动作库需要调整成适合项目的结构。」**

不要把 `muscle_map.json` 原样丢给 AI。生成 `Data/movements.json`，每条动作统一为：

```
{
  id, name_en, name_zh, category, lift,          // lift: S/B/D/null
  role,        // main | sbdVar | nonSbdVar | accessory
  level,       // main | primary_var | secondary_var | accessory
  pattern,     // squat | hinge | bench | vertical_push | horizontal_pull | ...
  equipment,   // barbell | dumbbell | machine | bodyweight | cable
  group,       // chest/shoulders/back/legs/arms/abs
  coef16: { ... },   // 16 叶系数；禁止 placeholder
  tier,        // A/B/C
  tags: [],    // 例如 low_bar, paused, deficit, competition
  plan_allowed, // true/false；不适合本项目的动作标 false 并写原因
  contraindications, // 伤病/关节限制
  source       // muscle_map / coefficient_matrix
}
```

规则：

- 261 个动作全部保留，但 `plan_allowed=false` 的动作 AI 不能选。
- 每个动作必须有完整 16 叶系数；缺系数 = 不可用，不能补 0 或猜。
- `role`/`level` 按老分类规则；8 个重点变式标 `primary_var`/`secondary_var`。
- 同动作不同 category 的向量必须区分；不能合并成一条。
- 动作库是 AI 计划生成的**唯一动作来源**；AI 不能发明新动作名。
- 0.01 先产出这个库 + 校验脚本（数量、缺系数、重复名、plan_allowed 原因）。

### 18.1 等效组数口径

- **SBD 等效组数** = 主项 sets + 变式 sets（每个动作按 lift 归属；每组计 1）。
- **肌群等效组数** = Σ(sets × 该动作对应肌群系数)，即 weighted；direct 另算。
- 周 MEV/MRV 和每周肌群等效组数是 AI 生成计划的硬约束。
- 过往计划完成率/达成率会调整下一周期的起始 volume/intensity；不是从零开始。

## 19. AI 计划生成（JAI 风格 + 本项目特色）

- Block 结构由 AI 按目标/周数/比赛日期决定；plan JSON 显式写 `blocks[]`、`weeks[]`、deload、test_plan。
- 每周训练日模板由 AI 按每周天数 1–6 生成；不固定 A/B/C/D，但 plan JSON 要显式写 days。
- 硬约束：每周 SBD 等效组数、肌群加权组数、MEV/MRV；不得超 MRV 或长期低于 MEV。
- 参考 Juggernaut AI 的块周期/递进/测试周；保留本项目特色：gear、GPP、readiness、body map、5 km、体重目标、比赛/非比赛测试。
- 输出 plan JSON 必须过 schema 校验；AI 不能直接写数据库，用户确认后才生效。
- 生成前给 AI 的输入：review JSON（执行/达成/结束水平）+ 问卷 + 动作库 + MEV/MRV + 过去 1–3 个周期摘要。

## 20. 技术选型与实施路线（2026-11-13 最终）

### 20.1 选型与理由

| 层 | 选择 | 体积 / 许可 | 为什么 |
|---|---|---|---|
| 前端 | Vue 3 + Vite | 产物约 60–70 KB gzip；MIT | 单文件组件 + Composition API，纯英文文档齐全，过渡/动画原生支持，长期好维护；不引 UI 库，视觉不被组件库绑死 |
| 动效 | Motion One | ~3 KB；MIT | 只补数字滚动、描边绘制这类“点睛”，不引入动画框架 |
| 后端 | FastAPI + SQLite | 依赖轻；MIT / Public Domain | 与统计、导入导出、DeepSeek 同为 Python；自动校验 + OpenAPI 文档 |
| 图表 | 全自绘 CSS + SVG | 0 | 复刻老站容量柱与肌群图，风格完全统一 |
| 人体底图 | `body-muscles@1.0.0` | Apache-2.0，路径 19,565 B | 前后双视图、70+ 区域，能对上 16 叶；不自己画人体 |
| 部署 | systemd + uvicorn + Nginx（或 Caddy） | — | 单进程够用；静态产物由同一域名提供 |

不选：React（易滑向卡片堆叠、产物大）、Svelte（生态与维护面小）、Django（过重）、Go（数据链要重写）、ECharts/Chart.js（默认观感与报表风冲突）。

### 20.2 数据模型

```text
cycles(id, name, start_date, end_date, status, schema_version)
plans(id, cycle_id, json, version, created_at)
logs(id, cycle_id, date, session_id, exercise_id, set_index,
     load, reps, rpe, set_count, note, updated_at)
readiness(id, date, fatigue, arousal, nutrition,
          hrv, sleep_score, rhr, session_time, rec, note)
archives(id, cycle_id, review_json, exported_at)
body_metrics(id, date, bodyweight, bodyfat, measurements_json)
```

- 计划 JSON：`RPL-Raw-v1`，顶层含 `schemaVersion`、`meta`、`blocks[]`、`weeks[]`、`testPlan`、`source`。
- 旧计划：`RPL-Plan-v4` 只经适配器转成 v1；转换结果过校验后才落库。
- 导入校验失败：拒绝导入 + 逐字段报错（文件、周、日、动作、字段、期望值），不做静默修复。
- API 前缀 `/api`：`/cycle`、`/plan`、`/log`、`/readiness`、`/analysis`、`/archive`、`/ai/chat`。
- 单用户：无登录；全站单份数据；写入冲突后写覆盖（后到者赢）。

### 20.3 准备度（建议，不自动改重量）

- 主观 3 项（1–7）：Muscle Fatigue / Neural Arousal / Nutrition。关节疼痛单独作为 flag，出现时给动作限制提示，不混进均分。
- 客观 3 项：HRV（ms）、Sleep Score（0–100，可退化用睡眠时长换算）、Resting HR（bpm）。缺失项跳过，不按 0 计。
- 归一化：主观按 `(v-1)/6`；客观按个人 28 天均值 ±2σ 截断归一；总分 `REC = clamp(0.75 + 0.5 × R/100, 0.55, 1.25)`。
- 时段修正：以 14:00–17:00 为基准；早晨 -3%、上午 -1.5%、傍晚 -1%（先经验系数）。训练时间与表现满 8 周后改用个人曲线。
- 输出：`Suggested today: -5%` 一类文案 + 一键撤销；**任何情况下不自动写回计划重量**。

### 20.4 人体肌群图规格

- 数据：`Ref/02_Stats/muscle_geo.json`，每叶带 `view: front|back|both`；渲染按 view 取舍。
- 色阶：单一色相 5 档，OKLCH 插值，固定端点；浅色模式由近背景色到深色强调；相邻档 ΔL ≥ 6。禁止 opacity 叠层与模糊滤镜。
- 线条：0.5–0.75px，肌肉间留 0.6px 白缝；无阴影、无渐变、无 3D。
- 编码：颜色 + 交互数值；点击/悬停显示 `weighted / direct / MEV / MRV / verdict`。
- 图例：5 档色块 + 区间值 + Primary/Secondary 标记；周选择 `< W01 >` 与 16 叶列表联动。
- 位置：Analysis 页主画面；Plan 底部容量区给精简版；**默认可见**，不藏在二级标签。
- 320px 不横向溢出；触控目标 ≥ 44px。

### 20.5 动效清单（只做这些）

1. 主项重量数字滚动（首次进入 Today 一次，约 500 ms）。
2. 主项重量“盖章”落位（1.04 → 1，轻微去模糊，约 200 ms）。

4. 折叠面板高度过渡 180 ms；切周内容横移 12 px + 淡入。

6. RPE 胶囊修改后微脉冲一次（约 180 ms）。
